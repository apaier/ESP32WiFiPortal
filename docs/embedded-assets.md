# Embedded assets

How files under `data/` end up compiled into the firmware, and why the library does that rather than read them off a filesystem at runtime.

## The contract

Any file dropped into `data/` (recursively) gets emitted as a `const uint8_t[] PROGMEM` byte array in `src/generated/embedded_assets.cpp` plus a declaration and length constant in `src/generated/embedded_assets.h`. A lookup function maps the file's relative path to a pointer + length:

```cpp
const uint8_t* getEmbeddedAsset(const char* name, size_t* outLen);
```

So `getEmbeddedAsset("WiFiSetup.html", &len)` returns the bytes of `data/WiFiSetup.html`. Subdirectories work too: `data/foo/bar.json` becomes `getEmbeddedAsset("foo/bar.json", &len)`.

The library uses this in [handleConfigPage](../src/ESP32WiFiPortal.cpp) to load the config form. Consumers can use the same function from their own routes if they put additional assets under `data/` (favicons, JSON blobs, anything small enough that compiling it in beats running a filesystem).

## How regeneration runs

[tools/embed_assets.py](../tools/embed_assets.py) is the regenerator. It walks `data/`, hashes nothing fancier than the rendered output (the script does its own check-before-write so it doesn't trip incremental builds), and emits `src/generated/embedded_assets.{h,cpp}`. Pure-stdlib Python; no third-party dependencies.

### PlatformIO

Automatic. `library.json` declares:

```json
"build": {
  "extraScript": "tools/embed_assets.py"
}
```

PlatformIO imports the script before compiling the library, the script runs unconditionally at import time, and any changes to `data/` flow into the build with no consumer-side configuration.

### Arduino IDE

Manual. Arduino IDE has no library-level pre-build hook a script can latch onto. The cost of supporting Arduino IDE is that the generated headers must be checked into the repository — that's why `src/generated/` is tracked in git.

If you edit anything under `data/`, run the regenerator once before compiling:

```sh
python3 tools/embed_assets.py
```

The script prints either `regenerated:` or `up to date:`, so it's safe to run repeatedly.

## Why this approach over LittleFS

The previous design read the HTML from `/WiFiSetup.html` on a LittleFS partition that the consumer uploaded separately (`pio run -t uploadfs` or the Arduino IDE filesystem plugin). Replacing it with build-time embedding:

- Removes the filesystem-upload step from the user's mental model and from the docs.
- Removes the LittleFS dependency from the library entirely. The flash savings (LittleFS code) more than cover the few-KB cost of the embedded HTML.
- Removes the partition-allocation concern; consumers don't have to budget flash for a filesystem they only use to ship one file.
- Keeps `data/` as the human-readable edit surface. The intent is that you edit a real `.html` file in a text editor, not a string literal in a C++ source file.

The compromise: changing the HTML requires a rebuild rather than a filesystem upload. For a config form that's edited once or twice over the device's lifetime, that's the right trade.

## Adding more assets

1. Drop the file into `data/` (or a subdirectory).
2. Rebuild (PlatformIO) or run `python3 tools/embed_assets.py` then rebuild (Arduino IDE).
3. Reference it from C++ via `getEmbeddedAsset("path/under/data.ext", &len)`.

Symbol names for the direct `extern` declarations are derived by replacing any non-alphanumeric character in the relative path with an underscore (`foo/bar.json` → `foo_bar_json`). Prefer the lookup function over direct symbol references unless you need a compile-time pointer — the lookup keeps the rest of your code path-driven rather than identifier-driven.

## Runtime override

If a consumer wants to swap the config form's HTML without editing `data/`, they can call:

```cpp
portal.setHtml(myHtmlBytes, myHtmlLen);
```

before `begin()`. The pointer is not copied; the caller owns the lifetime (typically a `PROGMEM` literal or another embedded asset). This bypasses the lookup entirely.
